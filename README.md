# Logo Repository

A centralized repository for SVG logos used across the mediNix ecosystem and other projects.

The repository has a deliberately simple architecture:

```text
logos/*.svg
      │
      ▼
tools/build-sprite.py
      │
      ▼
dist/icons.svg
      ▲
      │
GitHub Actions
```

The individual SVG files are the **source of truth**.

The generated SVG sprite is a build artifact that combines all logos into a single reusable SVG file.

---

## Purpose

This repository provides a clean and centralized location for service and infrastructure logos.

Instead of storing copies of the same SVG files inside multiple projects, applications can consume the generated sprite:

```text
dist/icons.svg
```

Each logo becomes an SVG `<symbol>` with a stable identifier derived from its filename.

For example:

```xml
<symbol id="seerr" viewBox="0 0 ...">
    ...
</symbol>
```

A consuming application can then reference the logo by its ID:

```html
<svg>
    <use href="/icons.svg#seerr"></use>
</svg>
```

This keeps logo assets separate from the applications that use them.

# `logos/` — Source of Truth

The `logos/` directory contains the original SVG logo files.

Every SVG in this directory represents one independent logo.

For example:

```text
logos/jellyfin.svg
logos/seerr.svg
logos/navidrome.svg
```

These files are the authoritative source assets.

The generated sprite should **never be edited manually**.

If a logo needs to be changed, replace or update the corresponding file in `logos/` and let the build process regenerate the sprite.

---

# Logo Naming

The filename determines the public sprite ID.

Examples:

```text
seerr.svg
    ↓
seerr

jellyfin.svg
    ↓
jellyfin

pocket id.svg
    ↓
pocket-id
```

The builder normalizes filenames into safe lowercase IDs.

Characters that are not valid in the generated identifier are converted into `-`.

This gives the generated sprite a predictable naming scheme.

The filename is therefore part of the public interface.

If a consuming application references:

```html
<use href="/icons.svg#seerr"></use>
```

the source file must remain:

```text
logos/seerr.svg
```

unless the consumer is intentionally updated as well.

---

# One Logo = One Public ID

The generated sprite deliberately exposes exactly **one public `id` per source SVG**.

For example:

```xml
<symbol id="acme">
    ...
</symbol>

<symbol id="audiobookshelf">
    ...
</symbol>

<symbol id="seerr">
    ...
</symbol>
```

The builder removes internal SVG element IDs from the imported source files.

This prevents the generated sprite from exposing additional IDs such as:

```text
acme-path1
acme-defs1
acme-g14
```

The public sprite API therefore remains simple:

```text
acme
audiobookshelf
bitwarden
caddy
...
seerr
sonarr
unraid
```

One source SVG corresponds to one sprite symbol and one public symbol ID.

# `tools/build-sprite.py`

The sprite is generated by:

```text
tools/build-sprite.py
```

The script intentionally uses only Python's standard library.

Its job is to:

1. Find all `.svg` files in `logos/`.
2. Sort them deterministically.
3. Parse each SVG.
4. Validate that the source document is an SVG.
5. Determine its `viewBox`.
6. Normalize the logo filename into a sprite ID.
7. Convert legacy `xlink:href` attributes to modern `href`.
8. Remove internal SVG element IDs.
9. Create one `<symbol>` for each logo.
10. Add all symbols to one SVG sprite.
11. Write the result to:

```text
dist/icons.svg
```

The resulting sprite is deterministic: the same set of source SVGs produces the same logical sprite structure.

---

# SVG Compatibility

The builder also handles older SVG files that still contain:

```xml
xlink:href="..."
```

These references are converted to:

```xml
href="..."
```

This avoids carrying unnecessary legacy `xlink` namespace declarations into the generated sprite.

The generated sprite therefore uses modern SVG references wherever the source files permit it.

---

# `viewBox`

Every logo needs a usable coordinate system.

The builder first uses the source SVG's:

```xml
viewBox="..."
```

If no `viewBox` exists, it falls back to the source `width` and `height` values.

For example:

```xml
width="100"
height="100"
```

becomes:

```text
0 0 100 100
```

If neither a `viewBox` nor usable dimensions exist, the build fails instead of generating an invalid symbol.

---

# Generated Sprite

The final artifact is:

```text
dist/icons.svg
```

It contains all logos as `<symbol>` elements inside one SVG document.

Conceptually:

```xml
<svg xmlns="http://www.w3.org/2000/svg" aria-hidden="true">

    <symbol id="acme" viewBox="...">
        ...
    </symbol>

    <symbol id="audiobookshelf" viewBox="...">
        ...
    </symbol>

    <symbol id="seerr" viewBox="...">
        ...
    </symbol>

</svg>
```

The sprite can therefore be served as one static asset.

SVG symbol sprites are a common pattern for combining multiple SVG graphics into a single reusable document.

---

# Using the Sprite

A consuming application can reference an individual logo with `<use>`.

Example:

```html
<svg aria-hidden="true">
    <use href="/icons.svg#seerr"></use>
</svg>
```

Another example:

```html
<svg aria-hidden="true">
    <use href="/icons.svg#jellyfin"></use>
</svg>
```

The complete sprite remains one file:

```text
/icons.svg
```

while the fragment identifier selects the required symbol:

```text
/icons.svg#seerr
/icons.svg#jellyfin
/icons.svg#navidrome
```

This allows applications to use the same centralized asset collection without maintaining individual copies of every logo.

---

# `experiments/`

Experimental or unfinished assets do not belong in the production logo collection.

They can be kept separately under:

```text
experiments/
```

Files in this directory are intentionally ignored by the sprite builder.

The builder only reads:

```text
logos/*.svg
```

Therefore an experimental SVG cannot accidentally appear in the production sprite simply because it exists somewhere else in the repository.

# Automated Build

The repository contains a GitHub Actions workflow:

```text
.github/workflows/build-sprite.yml
```

The workflow automatically rebuilds the sprite when relevant source files change.

The workflow watches:

```text
logos/**/*.svg
tools/build-sprite.py
```

Therefore:

```text
new logo
    ↓
logos/new-service.svg
    ↓
git push
    ↓
GitHub Actions
    ↓
build-sprite.py
    ↓
dist/icons.svg
```

The workflow then checks whether the generated sprite actually changed.

If nothing changed, no commit is created.

If the sprite changed, GitHub Actions commits the updated:

```text
dist/icons.svg
```

and pushes it back to `main`.

---

# Why the Generated Sprite Is Committed

`dist/icons.svg` is a generated artifact, but it is intentionally committed to the repository.

This makes the repository immediately consumable without requiring every consumer to run the Python build process.

Consumers can simply fetch:

```text
dist/icons.svg
```

The repository therefore provides both:

```text
Source:
logos/*.svg
```

and:

```text
Ready-to-use artifact:
dist/icons.svg
```

The build process keeps the two synchronized.

---

# Adding a New Logo

Adding a new logo is intentionally simple.

Copy the SVG into:

```text
logos/
```

For example:

```text
logos/plex.svg
```

Then commit and push:

```bash
git add logos/plex.svg
git commit -m "add plex logo"
git push
```

GitHub Actions automatically rebuilds the sprite.

The resulting symbol will be:

```xml
<symbol id="plex">
```

No modification to:

```text
tools/build-sprite.py
```

is required.

No modification to the GitHub Actions workflow is required.

No central logo registry needs to be updated.

---

# Updating a Logo

To replace an existing logo, simply replace its source SVG.

For example:

```text
logos/seerr.svg
```

After pushing the change, the automated build regenerates:

```text
dist/icons.svg
```

The public ID remains:

```text
seerr
```

as long as the filename remains unchanged.

# Design Principles

The repository follows a few deliberate principles.

## Source over generated data

```text
logos/
```

is authoritative.

```text
dist/
```

is generated.

Never manually modify the generated sprite.

---

## One source asset, one public identity

Every production SVG corresponds to exactly one public symbol ID.

This keeps the sprite predictable and easy to consume.

---

## No central registry

There is no manually maintained list such as:

```text
logos = [
    "jellyfin",
    "seerr",
    "navidrome",
    ...
]
```

The filesystem itself is the registry.

If an SVG exists in:

```text
logos/
```

it becomes part of the sprite.

---

## No application-specific logic

The logo repository does not know anything about the applications consuming the logos.

It does not contain:

* service configuration
* reverse-proxy configuration
* DNS configuration
* application metadata
* UI routing
* application-specific HTML
* application-specific JavaScript

It only manages logos and their generated sprite.

---

## Deterministic automation

The build process should always be reproducible from the source directory.

The intended relationship is:

```text
logos/
   ↓
builder
   ↓
sprite
```

There should be no manual step between adding a logo and updating the generated sprite.

---

# Relationship to Other Projects

This repository is designed to be consumed by projects such as mediNix.

For example, a mediNix landing page does not need to contain the SVG source code for every supported service.

Instead, it can reference the centralized sprite:

```html
<svg>
    <use href="/icons.svg#jellyfin"></use>
</svg>
```

The consuming project only needs to know the public symbol ID.

The actual SVG artwork remains maintained here.

This creates a clean separation:

```text
logorepo
    │
    │ provides
    ▼
icons.svg
    │
    ├── jellyfin
    ├── seerr
    ├── audiobookshelf
    ├── navidrome
    └── ...
    │
    ▼
consuming applications
```

# Summary

The repository is intentionally small.

Its core contract is:

```text
logos/*.svg
    ↓
tools/build-sprite.py
    ↓
dist/icons.svg
```

GitHub Actions maintains the generated artifact automatically.

Adding a logo means adding one SVG file.

The filename becomes the symbol ID.

The builder creates one `<symbol>` per logo.

The generated sprite contains one public ID per source SVG.

Applications consume the resulting sprite through standard SVG `<use>` references.

This makes `logorepo` a simple, centralized and automatically maintained source of SVG logos for the wider mediNix ecosystem.
